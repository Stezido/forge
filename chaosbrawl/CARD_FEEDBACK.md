# Forge card-feedback checklist

For owner card feedback, first read the companion website workflow: `docs/card-feedback-mse-forge.md` in `Stezido/Chaosbrawl-Website` (local repository `/home/stefan/github/Chaosbrawl-Website`; use a clean isolated worktree for changes). It covers authoritative MSE edits, owner-chat/Tavern authorization, native exports, cross-repository PRs and release boundaries.

1. **Verify the rule.** Read the registered development `.mse-set` and import metadata, not an old rendered image, historical batch or remembered rule. Decide whether MSE design/text needs changing or whether Forge alone is wrong. Preserve printed timing/costs/targets unless the owner explicitly changes them. Beer remains sorcery speed; improving AI mana planning does not authorize opponent-turn activation.
2. **Trace the implementation.** Find stable card IDs/native UIDs, executable abilities, SVar/subability chains, printed Oracle, tokens, edition/functional variants and image keys. Check all related cards when a shared mechanic is involved. Use native full-card token renders, never illustration crops. Keep upstream behavior outside opt-in Chaos Brawl unchanged.
3. **Sync reviewed provenance.** After an MSE change is validated and committed, add a reviewed batch containing changed imported records with the same native UIDs, exact website commit and archive SHA256. Preserve older batches. Supply current supporting tokens and generated-only IDs. Refresh the complete executable hash manifest after review/checks, including new helpers and modified AI/controller code. Preparation must verify both the registered source hash and executable hashes.
4. **Test the actual bug.** Use real custom printings and relevant phases, target restrictions, payment and stack/trigger order. Verify conditional damage both ways, counter movement choices, self-sacrifice trigger snapshots, tolerance boundaries and optional choices as relevant. Run `bash chaosbrawl/forge.sh test` in an isolated test profile. For AI changes, verify chosen targets, phase/timing, useful versus unavailable responses, real colored mana preservation and a decision through the controller when relevant. Do not globally classify all Drunken counters as harmless or all friendly Obsession counters as beneficial.
5. **Check generated pools.** AJDE! stays a real generated-only sorcery created by Windtongue, excluded from every ordinary/wildcard/land/planeswalker booster sheet and starting deck. Preserve conjuring. Keep `generatedOnlyIds` and shared website eligibility coherent even with older frozen catalogue metadata. When relevant run `python3 chaosbrawl/limited/generate.py --check` and `bash chaosbrawl/forge.sh test-limited`; preserve the single 50% common-to-land slot and 2% rare-to-planeswalker slot unless the owner changes them.
6. **Prepare and inspect.** Run `python3 chaosbrawl/prepare.py --website <verified-website-worktree>` against the new source and SHA-keyed native renders. Confirm the selected batch is current for preparation, Windows packaging and Adventure. Review actual image lookup paths and full token faces. Build affected desktop/mobile modules where applicable. Never replace a running user's installed package, decks or profile during local checks.
7. **Commit and review.** Push to the `private` remote (`Stezido/Chaosbrawl-Forge`), not the legacy `origin` (`Stezido/forge`). Open a PR targeting the existing custom release branch, cross-link the website source PR, record observed checks and merge approved fixes according to `AGENTS.md`. Preserve existing branches/PRs and disabled private Actions.
8. **Respect release cadence.** A fix/merge is not authorization for a new downloadable release. Leave existing published binary/source assets immutable and accumulate fixes until explicitly asked for another release. When asked, follow existing Windows/Android packaging runbooks, ship matching GPL sources, preserve Android application/signing identity and minimum supported version, and test upgrades with existing decks/resources. Never claim physical-device performance from desktop or emulator-only checks.

Report source changes, engine changes, test evidence and release status separately. If a source rule was already correct, say so; if a released binary still predates the fix, say so.
